# Plugins

> Extend undocs with npm packages — server hooks for the content engine and Nitro,
> client hooks for navigation, search, and chrome — without forking the theme.

Most docs sites need only Markdown and `docs.yaml`. When you want behaviour that
does not belong in core — locale routing, custom blog rules, extra header
controls, hreflang tags — ship it as a **plugin** instead of patching undocs
itself.

Plugins are declared in config, loaded once at build time, and run through a
single client **PluginHost** so the Vue app stays unaware of any one extension.

## Enable a plugin

Add entries to `plugins` in `.config/docs.yaml`:

```yaml
plugins:
  - "@undocs/i18n"
  - package: "./plugins/my-extension"
    options:
      defaultLocale: en
```

Each entry is either a package name (or path relative to the docs directory) or
an object with `package` and optional `options`. Options are passed to every
server hook for that plugin; client hooks receive the merged docs config the
server plugins produced.

## Package layout

A plugin can export **server only**, **client only**, or a **bundle** with both.

| Export                                                                 | Resolved as                                               |
| ---------------------------------------------------------------------- | --------------------------------------------------------- |
| Default object with `server` / `client` keys                           | Bundle (`defineUndocsPluginBundle`)                       |
| Default object with `name` and hooks, no `server`/`client` keys        | Server plugin                                             |
| `./server`, `./server.js`, `./server.ts`                               | Server entry                                              |
| `./client`, `./client.js`, `./client.ts`, or bundle root with `client` | Client entry (baked into the client bundle at build time) |

Local paths are checked on disk; npm packages resolve through the docs project's
`node_modules`. A plugin with no client entry is skipped on the client side —
server hooks still run.

Minimal bundle:

```ts
import { defineUndocsPluginBundle } from "undocs/plugin";

export default defineUndocsPluginBundle({
  server: {
    name: "my-plugin",
    appConfig(config, ctx) {
      // ctx.options — options from docs.yaml for this plugin
      return config;
    },
  },
  client: {
    name: "my-plugin",
    install(app, ctx) {
      // Optional: override <html lang> (must match on SSR and client)
      return { htmlLang: "de" };
    },
  },
});
```

Use `defineUndocsPlugin` when you export a single server or client object.

## Server hooks

Server plugins run in Node during config load, Nitro setup, and content indexing.
They never ship in the browser bundle.

| Hook                             | When it runs                                                                            |
| -------------------------------- | --------------------------------------------------------------------------------------- |
| `appConfig`                      | Before `virtual:undocs/app-config` is emitted — mutate theme config, inject docs fields |
| `nitro`                          | While `nitro.config.ts` is evaluated — `runtimeConfig`, prerender routes, route rules   |
| `vite`                           | Dev/build — return extra Vite plugins and directories that should reload app-config     |
| `content.buildOptions`           | Before the content index is built — adjust `dir`, `automd`, …                           |
| `content.excludeFromOrder`       | Prev/next ordering — return `true` to drop a path (default excludes `/blog/**`)         |
| `content.acceptSurroundNeighbor` | Prev/next pairing — return `false` to block a neighbor                                  |
| `content.isBlogPost`             | `/api/docs/blog.json` membership                                                        |
| `content.classifyPath`           | Optional path role (`blog`, `home`, …)                                                  |

Hooks run in registration order. Return `undefined` from a boolean hook to defer
to the next plugin; the first definitive `true` or `false` wins where documented
above.

## Client hooks

Client plugins are statically imported at build time and reduced by **PluginHost**
— one runner the core calls instead of branching on feature flags.

| Hook            | Purpose                                                                                  |
| --------------- | ---------------------------------------------------------------------------------------- |
| `install`       | Run once from `main.ts` and `entry-server.ts`; register globals; optional `{ htmlLang }` |
| `routes`        | Prepend custom routes before the docs catch-all                                          |
| `navigation`    | Transform the sidebar tree after content filtering                                       |
| `docsConfig`    | Per-route chrome (`landing`, `banner`, …)                                                |
| `filterPath`    | Drop paths from search and WebMCP (`false` hides)                                        |
| `head`          | Extra unhead entries — `meta`, `link`, and `script` arrays merge across plugins          |
| `components`    | MDC / global Vue components (merged after built-ins)                                     |
| `headerActions` | Components in the desktop header cluster (`PluginChrome`)                                |

`install` must behave identically on SSR and the client — that is what keeps
hydration stable. The router is ready before `install` on the server so
`ctx.route` matches the requested path.

## What core wires for you

You do not import PluginHost in your plugin. Core already connects hooks at the
integration points:

- **Router** — `pluginHost.routes()` prepends plugin routes.
- **Sidebar** — navigation pipeline in `app.vue`.
- **Search** — `filterPath` before results are shown (including empty-query sections).
- **WebMCP** — same `filterPath` gate as search.
- **Markdown** — plugin components merged into `MarkdownRenderer`.
- **`<head>`** — plugin `head` entries merged in `app.vue`; `htmlLang` from `install` sets `html lang`.

Server content hooks apply to the live index (`getIndex()`), API routes, and the
dev watcher — not only the initial build.

## Authoring tips

**Keep hooks pure where you can.** Server hooks may run concurrently across
requests only where documented (content index is process-cached); do not stash
mutable state on module scope in client code that runs during SSR render.

**Prefer bundles for i18n-style features.** One package, two entries, shared
`options` — the pattern `@undocs/i18n` is expected to follow.

**Client-only UI belongs in `headerActions` or `components`**, not scattered
patches across core Vue files. That is the point of the SDK.

**Test locally** with a relative path before publishing:

```yaml
plugins:
  - package: "../packages/my-plugin"
    options: { debug: true }
```

See `test/fixtures/plugins/echo/` in the undocs repository for a reference plugin
that exercises every hook.
