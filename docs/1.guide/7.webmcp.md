# Browser agents (WebMCP)

> Your docs site hands its own search and navigation to the user's browser AI agent as MCP tools.

[WebMCP](https://webmachinelearning.github.io/webmcp/) is a draft web standard
that lets a page register MCP tools with an AI agent running in the browser:

```js
await document.modelContext.registerTool({ name, description, inputSchema, execute });
```

Instead of the agent scraping rendered HTML, the page tells it what it can do.
undocs registers a small set of docs tools automatically — no configuration, no
extra script tag.

## The tools

| Tool               | Does                                                                          |
| ------------------ | ----------------------------------------------------------------------------- |
| `search_docs`      | Full-text search over every page and heading, with previews and linkable URLs |
| `list_pages`       | Every page in navigation order, with its path and description                 |
| `get_project_info` | Repository, issues, releases, social links, `llms.txt`, versions              |
| `read_page`        | The Markdown source of one page, sliced with a cursor if it is long           |
| `get_current_page` | The page the user is looking at, plus its heading outline                     |
| `navigate`         | Opens a page (optionally at an anchor) in the user's tab                      |

They run against the machinery the page already owns: `search_docs` queries the
same MiniSearch index that powers <kbd>⌘K</kbd>, and `read_page` returns the same
Markdown that `/llms.txt` links to. An agent therefore searches
exactly what a visitor searches — no separate index to keep in sync, and answers
are grounded in the docs rather than in a model's memory of them.

## Links, not resources

MCP has a `resources` primitive; WebMCP does not — `document.modelContext` is
`registerTool` / `getTools` / `ontoolchange` and nothing more. So the things you'd
otherwise attach as resources are returned _by_ tools instead:

- `get_project_info` derives your repository, issue tracker, releases, community
  links, `llms.txt` bundles and versions from `.config/docs`. It uses the same
  conventions the header and footer render, so an agent and a visitor get the
  same links.
- Every page result carries `url`, `markdownUrl` (its `/raw/*.md` source) and
  `editUrl` (the "edit this page" link on GitHub). Generated routes — the landing
  page, the blog listing — have no Markdown behind them, so those two are simply
  absent rather than pointing at a URL that 404s.

Only `navigate` changes what the user sees; the rest are marked `readOnlyHint`.
Every tool that returns docs prose sets `untrustedContentHint`, so a well-behaved
agent treats it as data and never as instructions. `navigate` also refuses a path
that isn't a real route, so a mistyped link can't strand the reader on a 404.

## Browser support

WebMCP is early — `document.modelContext` exists only in browsers implementing
the draft, and only in a secure context (HTTPS or `localhost`). undocs
feature-detects it and loads the integration as its own lazy chunk, so a browser
without WebMCP downloads nothing at all.

## Opting out

```ts [.config/docs.ts]
export default {
  webmcp: false,
};
```
